### 4-2. 다른 분류 담당과 맞출 것 (MyClaw 분석)

- **① 서버 처리 담당(D9)**: API 분류 상세 설계는 인증·초기 설정·AI 처리·확인형 AI·AI 비서에만 있다. 아래 담당 항목은 서버 쪽 작업이 필요한데 대응하는 API 항목이 없다.
  - 저장·조회: DTL-CAL-002(일별 목록 조회), DTL-CAL-003(일정 등록·수정·삭제), DTL-TSK-002(완료 상태 저장), DTL-INB-002(태그·프로젝트·담당자 목록), DTL-PRJ-002(배정 저장)
  - 파일 보관: DTL-INB-007
  - 예약 작업: DTL-BRF-001(설정 시각 발송), DTL-BRF-002(일정 15분 전 발송), DTL-SYS-001(30일 보관 기한. 기한 뒤 자동 파기인지는 시트에 없어 팀 확인)
  - 인증: 인증 코드 확인(DTL-AUT-027 ※)과 토큰 재발급(DTL-AUT-037, DTL-AUT-038 ※)도 API 분류 항목이 따로 없다.
- **② AI 응답에 근거 위치**: DTL-UX-005는 추출 항목의 원본 문장으로 스크롤·하이라이트해야 하는데, DTL-AI-005가 돌려주는 항목은 "메모, 할일, 일정, 프로젝트, 인물(담당자), 장소, 중요도, 날짜"뿐이다. 추출 항목마다 원문 위치(텍스트는 문자 범위, 음성은 STT 시각)를 돌려주도록 API 담당과 형식을 정한다. 음성이면 DTL-AI-001의 변환 결과에 시각 정보가 있어야 한다. 같은 합의에서 제목과 일시 필드도 정한다. 카드(DTL-UX-002)는 '추출된 제목'과 '일시'를 보여 주고 DTL-UX-004는 "요약 제목이나 날짜"를 고치는데, DTL-AI-005의 항목에는 제목이 없고 시각 없이 날짜만 있다. 합의 전에는 DTL-UX-003·004를 임시 타입으로 만든다(4-3).
- **③ 일정·할 일에 원본 연결**: DTL-UX-006은 'AI 제안 후 사용자 확정' 출처 구분값만 저장한다. DTL-UX-005의 근거 보기와 DTL-AST-003의 출처 링크 칩은 원본 메모 ID가 있어야 한다. 일정·할 일 저장 형식에 원본 메모 ID와 근거 위치를 넣고, DTL-AST-002의 답변에도 출처 ID를 담도록 정한다.
- **④ 제한 수치의 서버 적용**: DTL-AUT-026의 "재발송은 1시간에 최대 5회"는 화면에서만 막으면 우회할 수 있다(일반 지식). DTL-AUT-022(API) 담당과 서버에서도 막을지 정한다. DTL-AUT-022 비고 "수치 백엔드 협의"(D6)와 함께 정하면 된다. 또 5회를 넘겼을 때의 문구와 차단 시간을 적은 항목이 시트에 없고, 가입 직후 자동 발송(DTL-AUT-022)이 횟수에 드는지도 없다. 예외 분류 담당과 함께 정한다. 그 전까지 DTL-AUT-026은 60초 부분만 만든다(4-3).
- **⑤ 토큰 흐름**: DTL-AUT-037·038은 DTL-AUT-036(토큰 저장 방식)·040(Refresh 토큰 회전), DTL-AUT-035(로그인 유지)에 기댄다. DTL-AUT-040은 "이미 폐기된 토큰이 재사용되면 탈취로 간주"한다. 그래서 동시 만료 때 갱신을 1회만 보내는 DTL-AUT-038이 빠지면 정상 사용자가 모든 기기에서 로그아웃될 수 있다. 보안 담당과 같은 재발급 방식을 쓴다. 탭이 여러 개일 때도 같은 위험이 있다(추론). Access 토큰은 탭마다 메모리에 따로 있고(DTL-AUT-036) Refresh 토큰 쿠키는 함께 쓴다. 그래서 두 탭이 동시에 갱신하면 나중에 처리된 요청이 폐기된 토큰의 재사용으로 판정될 수 있다. DTL-AUT-038의 "갱신 요청은 1회만"을 탭 사이에도 적용할지 보안 담당과 정한다.
- **⑥ 결정의 영향**: D2 — 웹 전제 상세 설계 12건 가운데 6건이 담당이다(DTL-AUT-037, DTL-SET-014 ※, DTL-INB-007, DTL-AI-004, DTL-CAL-002, DTL-SYS-002). 모바일 앱으로 가면 이 6건을 다시 쓴다. D3 — DTL-AI-004. D4 — DTL-PRJ-002(B2B).
